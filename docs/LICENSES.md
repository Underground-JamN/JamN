# Licenses

JamN's own code is **MIT** (see `LICENSE`). This file tracks the license of
every dependency the build touches, and the one recurring decision that
needs revisiting if this project's circumstances change: JUCE's revenue cap.

## JUCE

**License track:** JUCE 8.0.9 (SHA-pinned in `CMakeLists.txt`) is
dual-licensed AGPLv3 / JUCE 8 EULA - the dual grant is stated in the
pinned checkout's own `LICENSE.md`, even though the EULA text itself never
mentions AGPL. JamN uses the **EULA's Starter tier** (free, no seat
purchase; no splash-screen clause appears in the JUCE 8 EULA text, unlike
older JUCE versions), fetched via
`FetchContent` at build time - never vendored into `third_party/`. The
EULA forbids redistributing "the Framework... on its own," so
`FetchContent` is also the only distribution-safe option regardless of
tier.

**The constraint that matters:** Starter tier is capped at **$20,000
revenue over any rolling previous-12-months window** (not calendar-year),
and the cap's definition depends on who the Licensee is:

- *Individual:* revenue or funding generated by that individual's use of
  the Framework, from all sources - donations, sponsorship, ads and other
  indirect revenue included, not just direct sales.
- *Entity:* **total revenue of the entity and all its Affiliates, from all
  sources, whether connected to JUCE use or not.** If JamN were ever
  developed under a company/LLC, unrelated company income counts against
  the $20,000.

Exceeding the cap is not a grace period: EULA section 1.14 requires either
purchasing the appropriate tier or *immediately ceasing to develop and
Distribute* the product.

**Trigger to revisit:** if this project ever meaningfully monetizes (a
popular Patreon, ads, a paid tier), move to the **Indie** tier ($40/mo per
user or an $800 one-time perpetual license, capped at $300,000/year;
Pro above that: $175/mo per user, 12-month minimum, or $3,500 perpetual)
*before* that revenue is taken, not after. Note the per-user pricing if
there is ever a second developer at that point. This is the one license
decision in this file that is not a set-and-forget - check this section
before adding any monetization.

**The AGPLv3 fallback:** JamN's own code is MIT (AGPL-compatible) and the
full source is public, so distributing builds under JUCE's AGPLv3 track
looks compliant on its face and has *no revenue cap at all*. It is not the
default here for two reasons: it would force the combined distributed app
onto AGPLv3 terms rather than a clean MIT story, and it would foreclose
the planned proprietary-route ASIO build (same GPL-incompatibility
reasoning as the ASIO section below). If this route is ever actually
taken, AGPLv3's section 13 (source offer to users interacting *over a
network*) needs real analysis first - JamN is a peer-to-peer networked
app, the exact fact pattern where that clause may be live rather than
dormant, and nobody has read the AGPL text against it yet. An
escape-hatch candidate if the cap ever binds, not a pre-cleared one.

**Version pin note:** JUCE's current `master` now points at a *JUCE 9*
EULA. The 8.0.9 pin keeps JamN under the JUCE 8 terms described here; any
future upgrade past 8.x means re-reading a new EULA, not assuming these
terms carry over.

**Licensee / track recorded:** Entity - `Underground-JamN`, Starter tier
EULA (see above). The $20,000 cap applies to the entity's total revenue
from all sources, whether connected to JUCE use or not.

## VST3 SDK

**License:** MIT, since VST3 SDK version 3.8 (relicensed ~October 2025).
Steinberg's own developer portal states plainly that the older
GPLv3/proprietary dual-license option "is no longer available" - MIT is now
the only option, with no fees, no membership and nothing to sign.

**Practical effect:** when Phase 3c (VST3 hosting) is built, use a
self-fetched SDK >= 3.8 directly under its MIT terms like any other
`third_party/` dependency - no special build gating is needed for
licensing reasons. **But not via JUCE's bundled copy:** the VST3 snapshot
vendored inside JUCE 8.0.9 (`modules/juce_audio_processors/format_types/
VST3_SDK/`) is labeled "Proprietary Steinberg VST3 License/GPLv3" in
JUCE's own `LICENSE.md` - the older dual license, not MIT. If Phase 3c
goes through JUCE's plugin-hosting classes, check which SDK copy actually
gets compiled in before assuming the MIT terms apply.

## ASIO SDK

**License:** dual GPLv3 / proprietary. Unlike VST3, this did not simplify -
Steinberg added GPLv3 as a new option in 2025 but kept the proprietary
option rather than replacing it, and the proprietary option still requires
signing a separate agreement and still restricts redistribution of the SDK.

**Practical effect:** ASIO support is opt-in and gated behind
`JAMN_ENABLE_ASIO=ON`, off by default, pointing at a user-supplied SDK path
under `third_party/asiosdk/` that is never committed (already excluded in
`.gitignore`). When that build is actually implemented, take the
proprietary route, not GPLv3 - taking GPLv3 would pull the combined binary
into GPLv3 compliance, which is incompatible with shipping MIT. This is
deferred work, not currently scheduled.

Every `third_party/<name>/` directory must carry its own `LICENSE` and
`PROVENANCE.md` - this project has no CI (see `AGENTS.md`'s Definition of
done), so it is enforced by whoever reviews the PR actually checking for it,
not just a convention left to memory.

## SoundFonts

Never shipped. Banks are user-supplied from a local, user-configured
directory and referenced by `{bank_name, sha256, preset}`, never
distributed with the repo or a release - their (mixed, sometimes unknown)
licensing never enters this analysis.
